    项目说明¶

    一、RadAlign：基于复合奖励的放射学视觉语言模型对齐¶

    1.1 数据集¶

    名称：MIMIC-CXR-JPG（报告生成任务）

    大小：

    • SFT 阶段：~10 万条 image-text pairs
    • GRPO 阶段：~10 万条 prompt-image pairs（与 SFT 同源，去掉答案）

    内容：美国医院胸部 X 光正位片 + 放射科医生手写 findings。每张图片对应一段报告，问句有 15 种自然语言变体随机采样。图像来源：MIMIC-CXR-JPG。

    图片规格：灰度图（单通道），原始分辨率约 2320×2828 像素，JPG 压缩后约 100-300 KB/张。模型输入时 Qwen3-VL 动态分块为多个 448×448 的 patch，每张胸片约产生 300-600 visual tokens。

    数据清洗：用 GPT-4o 从原始报告中抽取 findings 段，并删除"compared to prior exam"等历史对比句，只保留对当前片子的描述。

    报告长度：正常报告约 207 个字符（30-50 个英文单词），两三句话，属于短文本生成任务。

    格式（LLaVA / ShareGPT 风格）：

    {
  "image": "mimic_cxr/xxxx.jpg",
  "conversations": [
    {"from": "human", "value": "<image>\nProvide a radiology report for this Chest X-Ray."},
    {"from": "gpt",   "value": "PA and lateral views of the chest demonstrate clear lungs. No focal consolidation..."}
  ]
}

    1.2 训练流程¶

    SFT 阶段¶

    • 框架：LLaMA-Factory + DeepSpeed ZeRO-3
    • 底座：Qwen3-VL-8B-Instruct，全参数微调，bf16（选 Instruct 版本是因为已完成指令对齐，SFT 只需教放射学知识，无需额外数据教模型理解问答格式）
    • 数据：~10 万条，1 epoch
    • batch size：每卡 batch_size=4，梯度累积=4，等效全局 batch_size=128
    • 用卡：2 节点 × 4 卡 A100 80GB = 8 张 A100，ZeRO-3 跨节点分片
    • 训练时长：约 2 小时

    GRPO 阶段¶

    • 框架：verl + Ray

    • 数据：~10 万条（与 SFT 同源，去掉答案只保留图片+问题）

    • 用卡：共 4 节点 11 张 A100 80GB

    1. Actor：权重 bf16 16GB + 梯度 bf16 16GB + 优化器 fp32（master weight / fp32梯度 / m / v 各 32GB = 128GB）= 160GB，FSDP 分片 8 卡 → 20GB/卡，加激活值与通信缓冲实际 ~30GB/卡
    2. Reference：仅权重 bf16 16GB，冻结无梯度无优化器，PyTorch/FSDP 直接跑，不用 vLLM，不需要 KV cache（只做一次 log prob 前向，不做自回归生成），FSDP 分片 8 卡 → 2GB/卡
    3. vLLM Rollout：完整权重 bf16 16GB（不分片）+ KV cache ~30GB，2 卡分摊 → ~38GB/卡
    4. Reward Server：distilroberta-base（66M）+ bert-base-uncased CheXbert（110M）+ BioMedRoBERTa RadGraph-XL（125M），合计 ~300M 参数，fp32 约 1.2GB，加三个进程 CUDA context 实际 ~3-4GB，FastAPI 独立部署，与 Rollout 分节点避免 GPU 争抢
    角色 卡数 节点 显存
    Actor 8（2节点×4卡） 1-2 ~30GB/卡
    Reference 8（与Actor共卡） 1-2 ~2GB/卡
    vLLM Rollout 2 3 ~38GB/卡
    Reward Server 1 4 ~3-4GB
    合计 11 4 节点 —
    • 训练时长：约 8 小时（rollout 串行等待是主要耗时）

    1.3 奖励设计¶

    报告生成任务使用 -RadCliQ 作为奖励，RadCliQ 是四个指标的加权组合：BERTScore（语义相似）、CheXbert vector similarity（临床标签相似）、RadGraph F1（实体关系）、BLEU（字面 n-gram）。四个指标各自 z-score 归一化后加权求和，越低越好，取负号使其方向与 reward 最大化一致。

    三个神经网络奖励模型的输入输出：

    • BERTScore（distilroberta-base，66M）：输入两段文本（参考报告 + 生成报告），输出语义相似度 F1 分数，范围 0-1
    • CheXbert（bert-base-uncased，110M）：输入一段报告文本，输出 [CLS] embedding 向量（不使用 14 类病理分类头）；对参考报告和生成报告各提取一个向量后做余弦相似度（semb），理论范围 -1 到 1，实践中报告 embedding 方向相近基本落在 0-1
    • RadGraph-XL（BioMedRoBERTa，125M）：输入一段报告文本，输出实体（anatomy / observation）和关系（suggestive_of / located_at）构成的知识图谱；两张图分别计算实体集合 F1 和关系三元组 F1，取平均得到最终分数（范围 0-1）。关系必须 head、tail、type 三项全对才算命中，所以关系 F1 通常低于实体 F1

    三个模型输出经 z-score 归一化后加权求和，原始范围不影响 RadCliQ 最终计算。

    BLEU（统计公式，无模型）：统计生成报告中有多少 n-gram（1~4 元词组）出现在参考报告里，同时用 brevity penalty 惩罚过短的生成结果，输出 0-1。是纯规则计算，不需要神经网络。在 RadCliQ 中权重接近 0，实际贡献极小。

    例： - 参考："clear lungs no pleural effusion" - 生成："lungs are clear no effusion seen" - 1-gram 命中：lungs / clear / no / effusion → 精确率 4/7 ≈ 0.57

    1.4 关键工程问题¶

    FSDP 与 vLLM 内存布局不兼容：FSDP 权重动态分片、用完即丢；vLLM 权重必须静态常驻并预分配 KV cache，两者无法共用同一份显存布局。verl 的解法是维护两份独立副本——Actor/Reference 走 FSDP，Rollout 单独用 vLLM（TP=2），每步训练后从 Actor 同步权重到 vLLM，代价是显存翻倍。

    单一指标 reward hacking：实验发现只用 RadGraph-F1 作为奖励，模型会把报告缩短到 ~93 字符（正常约 207 字符），用极短文本刷高 F1——单一指标容易被钻空子。改用 RadCliQ 复合指标后 hacking 现象消失。

    1.5 源码框架 ❓¶

    SFT（LLaMA-Factory + DeepSpeed ZeRO-3）¶

    llamafactory-cli train
  └─ cli.py → launcher.py → tuner.run_exp()
                                   └─ run_sft()
                                        └─ CustomSeq2SeqTrainer（继承 HuggingFace Trainer）
                                             └─ HF Trainer 内部集成 DeepSpeed
                                                  └─ ds_z3_config.json（ZeRO-3 配置）

    DeepSpeed 不直接调用，通过 --deepspeed ds_z3_config.json 参数透传给 HF Trainer，LLaMA-Factory 本身不写 DeepSpeed API。

    GRPO（verl + Ray + FSDP + vLLM）¶

    sbatch / srun → Slurm 分配 4 个节点
  └─ 各节点启动 Ray
       └─ python -m verl.trainer.main_ppo  (algorithm.adv_estimator=grpo)
            ├─ main_ppo.py
            │    ├─ ray.init()               # 多机组 Ray 集群
            │    └─ RayPPOTrainer (ray_trainer.py)
            │         ├─ init_workers()      # 按角色分配 Ray Worker
            │         │    ├─ ActorRolloutRefWorker
            │         │    └─ RewardModelWorker
            │         └─ fit()
            │              └─ compute_grpo_outcome_advantage()  # core_algos.py
            └─ ActorRolloutRefWorker 内部
                 ├─ FSDP(Actor / Reference)
                 ├─ vLLM(Rollout)
                 └─ FSDPVLLMShardingManager

    各组件作用与关系：

    • verl：训练框架，实现 GRPO 算法主循环、advantage 计算、数据流转
    • Ray：分布式调度层，把不同角色分配到不同 GPU / 节点，管理进程间通信；每个 Ray actor 是独立进程，天然隔离 FSDP 和 vLLM 的显存布局
    • FSDP：PyTorch 原生分布式训练，对 Actor / Reference 做 ZeRO-3 式参数分片
    • vLLM：仅用于 Rollout 阶段做自回归生成，需要完整权重 + 预分配 KV cache
    • Slurm：集群任务调度系统，负责把任务提交到哪些机器、启动多机 Ray 集群，不属于代码内部组件

    🚗 实际链路：sbatch → Slurm 分配 4 个节点 → 各节点启动 Ray → ray.init() 组网 → verl 用 Ray 把 Actor/Rollout/Reward 绑定到具体 GPU。

    ActorRolloutRefWorker 内部（fsdp_workers.py）：

    ActorRolloutRefWorker
  ├─ FSDP(model)              # Actor / Reference → PyTorch FSDP 包装
  │    └─ FSDPEngine          # engine/fsdp/transformer_impl.py
  ├─ vLLMRollout              # Rollout → vllm_rollout_spmd.py
  │    └─ LLM(...)            # 直接调用 vllm.LLM
  └─ FSDPVLLMShardingManager  # fsdp_vllm.py：每步训练后同步权重 FSDP→vLLM

    自定义 Reward（custom_rewards/）：每个奖励模型包装为独立打分函数 compute_score()，通过 config 动态加载，HTTP 请求打到 FastAPI Reward Server。

    二、GENIUS：面向通用多模态搜索的生成式检索框架¶

    2.0 架构图¶

    2.1 数据集¶

    名称：M-BEIR（Multimodal BEnchmark for Instructed Retrieval，由 UniIR 提出，HuggingFace: TIGER-Lab/M-BEIR）

    大小（论文 Table 6）：

    项目 数量
    训练 query 1.1M
    验证 query 182K
    测试 query 190K
    候选库 5.6M

    内容：由 10 个子数据集合并而成（MS-COCO、Fashion200K、FashionIQ、VisualNews、NIGHTS、OVEN、EDIS、CIRR、InfoSeek、WebQA），覆盖 4 个领域、8 类检索任务：

    任务 query 类型 target 类型 示例数据集
    T→I 文本 图像 VisualNews, MSCOCO, Fashion200K
    I→T 图像 文本 VisualNews, MSCOCO, Fashion200K
    I→I 图像 图像 NIGHTS, OVEN
    T→T 文本 文本 WebQA
    (I,T)→I 图文 图像 FashionIQ, CIRR
    (I,T)→T 图文 文本 InfoSeek
    T→(I,T) 文本 图文 EDIS, WebQA
    (I,T)→(I,T) 图文 图文 OVEN, InfoSeek

    格式（query-target 对）：

    query:  一张红色运动鞋图片 + "找蓝色款"   （图 + 文）
target: 一张蓝色运动鞋图片               （图）

    数据预处理：M-BEIR 本身无需清洗或标注，下载后可直接使用；但 GENIUS 训练/推理前需要先用 CLIP-SF 对原始图文做一次特征提取，生成 extracted_embed/CLIP_SF/ 下的 .pt 文件。Stage 1 和 Stage 2 的训练直接读取这些预提取的 768 维 embedding，而不是原始图片/文本。特征提取脚本见 src/feature_extraction/run_feature_extraction_train.sh 与 run_feature_extraction_cand.sh。

    每条候选编码为 98 bits（2-bit 模态码 + 8×12-bit 语义码），比 CLIP 768 维 float 向量（≈3 KB）节省 99%+ 存储（论文 Table 7）。

    2.2 训练流程¶

    GENIUS 采用三阶段训练。Stage 0 直接复用 UniIR 预训练权重并冻结；Stage 1 学习将连续 embedding 量化为离散 ID；Stage 2 训练 T5 生成器学习 "query → target ID" 的映射。

    硬件与总耗时（论文附录 B.2）：

    阶段 GPU 耗时 说明
    Stage 0：CLIP-SF 预训练 4×RTX 3090 91h 这是 UniIR 预训练 CLIP-SF 的时间，GENIUS 直接复用权重并冻结
    Stage 1：残差量化器 4×RTX 3090 0.4h GENIUS 自身新增训练
    Stage 2：T5 生成器 4×RTX 3090 2h GENIUS 自身新增训练
    GENIUS 自身训练增量 — 约 2.4h 不计入 Stage 0 的 91h

    训练最久的是 Stage 0 的 CLIP-SF encoder，共 91 小时。但 GENIUS 论文将其视为已预训练好的组件直接加载，因此自身实际训练只有约 2.4 小时。

    Stage 0：多模态编码器（CLIP-SF）¶

    复用 UniIR 在 M-BEIR 上预训练好的 CLIP-SF（Score Fusion CLIP）权重，冻结参数仅做特征提取。GENIUS 自身不训练这一阶段。

    • 底座：OpenAI CLIP 双塔结构（ViT 图像塔 + Transformer 文本塔），代码中使用 ViT-L/14
    • 融合方式：图像向量与文本向量直接相加，即 fused_emb = img_emb + txt_emb
    • 输入输出：输入原始图文 → 输出 768 维融合向量；训练时 img_emb 与 txt_emb 分开保存，不预先相加
    • 耗时：CLIP-SF 预训练约 91h（不计入 GENIUS 训练开销），这是三阶段中训练最久的部分

    Stage 1：残差量化器（RQ）¶

    将 CLIP-SF 输出的 768 维连续向量量化为离散、分层的 ID 序列。

    • Combiner（图文自适应融合）：
    • 结构：4 个 MLP + 动态门控权重 w
    • 先分别把 img/txt 向量投影到 2560 维，拼接后经非线性融合，最终输出 combined + w × txt + (1-w) × img
    • w 由另一个 MLP + Sigmoid 从当前输入动态算出，决定更相信文本还是图像
    • 残差量化结构：
    • 共 9 层：第 1 层码本大小为 3（模态指示：0=图，1=文，2=图文），第 2~9 层码本各 4096
    • 每层量化上一层留下的残差，逐层逼近原始向量
    • 完整 ID 示例：<a0><b1234><c567><d890><e2345><f100><g3000><h2000><i1500>
    • 训练损失：三者联合优化
    • l_cl：对比损失，拉近 query 与 target 的融合向量。计算方式与 CLIP 的对称 InfoNCE 损失相同：对 query 和 target 做 L2 归一化后算 cosine 相似度矩阵，对角线为正例，对 query→target 和 target→query 两个方向分别算交叉熵再取平均；区别在于 CLIP 作用于 image-text 对，GENIUS 作用于 query-target 对，且 query/target 可以是图、文或图文任意组合 🚗
    • l_rq：量化损失，减少量化前后信息损失。计算方式：每层把输入向量与选中码字的差向量各维度平方后求和，9 层累加即为总量化损失
    • l_mse：MSE 损失，约束量化后的 query 与 target 仍接近。计算方式：对 batch 内每一对 query-target，分别经 RQ 量化重建为 768 维向量，逐维度求差后平方求和，再对所有 pair 取平均

    • 码本通过 EMA（decay=0.9）更新，不走梯度反传

      具体做法：每个训练 step 中，记录每个码字被哪些输入向量选中；对该码字本轮被分配到的所有输入向量求均值；然后用 EMA 公式更新该码字：新码字 = 0.9 × 旧码字 + 0.1 × 本轮被分配向量的均值。未被分配到的码字保持不动，长期未被使用的死码字会被重新初始化激活。 - 训练超参数（代码 residual_quantization/configs_scripts/large/train/inbatch/inbatch.yaml）： - 量化层数：codebook_level = 8（加上模态层实际为 9 层） - 每层码本大小：codebook_vocab = 4096 - batch size：2000 - epochs：21 - learning rate：1e-4 - 用卡：4×RTX 3090 - 用时：约 0.4h

    Stage 2：T5 生成器¶

    训练 T5-small 根据 query embedding 自回归生成目标候选的离散 ID 序列。

    • 底座：T5-small，但 num_layers = 0，即去掉 encoder，只保留 decoder
    • 输入处理：
    • query 经 CLIP-SF + Combiner 得到 768 维向量
    • embed_projector：Linear(768 → 512×30)，把向量展开为 30 个 T5 prefix token，作为 inputs_embeds 直接喂给 decoder
    • 查询增强（Query Augmentation）：
    • 训练时对 query 和 target 做 Beta(2,2) 混合：aug = √s × q_emb + √(1-s) × p_emb
    • 让模型见过"纯 query → 纯 target"之间的各种模糊输入，提升泛化能力
    • 词表初始化：
    • 为 9 层码本创建特殊 token，总数为 3 + 8 × 4096 = 32,771 个（第 1 层模态码 3 个 + 第 2~9 层语义码各 4096 个），如 <a0>、<b1234> 等
    • 用 RQ 码本中的码字向量初始化这些 token 的 embedding 与 lm_head：码本向量是 768 维，T5-small 的 embedding 维度是 512，因此先用 Linear(768 → 512) 做投影，再分别初始化 T5 的 shared 输入 embedding 层和 lm_head 输出预测层，最后调用 _tie_weights() 绑定两层
    • 这样 T5 从一开始就"认识"ID token 的语义
    • 训练超参数（代码 generative_retriever/configs_scripts/large/train/inbatch/inbatch.yaml）：
    • batch size：256
    • epochs：31
    • learning rate：1e-4
    • 查询增强参数：alpha = 2（对应 Beta(2,2) 分布）
    • 用卡：4×RTX 3090
    • 用时：约 2h

    2.3 推理流程¶

    训练完成后，检索分为离线索引与在线查询两个阶段。

    离线索引（候选库更新时执行）¶

    所有 candidate → CLIP-SF → 768维融合向量
                            ├→ Combiner → RQ → 9位 ID → 插入 Trie 前缀树
                            └→ rerank 向量 → 单独存为 .npy
    • Trie 只保留真实存在的 ID 路径

    在线查询¶

    Query (图+文+指令) → CLIP-SF → Combiner → q_emb
                                              │
                                              ▼
                                       embed_projector
                                              │
                                              ▼
                              T5 decoder + Trie 约束 beam search
                                              │
                                       K 条完整 ID 序列（K=10）
                                              │
                                              ▼
                              Trie 查 ID → K 个真实 candidate
                                              │
                                              ▼
                              Embedding Re-ranking（余弦相似度）
                                              │
                                              ▼
                                        Top-1 结果
    • 🚗 Trie 约束 beam search：Trie 是候选库所有合法 ID 序列的前缀索引，每个候选的 9 位 ID 对应 Trie 上一条根到叶子的路径。Beam search 每步先拿到当前已生成前缀，去 Trie 查该前缀下还能接哪些 token；只有 Trie 允许的 token 才参与下一轮概率排序，其余 token 被屏蔽。于是生成过程变成“在候选库 ID 集合上的约束搜索”：每条 beam 始终对应某个真实候选 ID 的前缀，最终输出的 K 条完整序列一定都是候选库里存在的合法 ID。简言之，Trie 负责“哪些路径能走”，beam search 负责“在能走的路径里选概率最高的”。最大路径长度为 9（1 位模态码 + 8 位语义码）
    • 重排：T5 beam search 生成 K 条完整 ID → 通过 Trie 找到对应真实 candidate → 用 query 与该 candidate 的 rerank 向量算余弦相似度 → 按相似度排序得到 Top-K
    • 速度（论文 Section C.3，单张 RTX 3090，文搜图任务）：
    • beam=30：19.6 QPS（≈51 ms/query）
    • beam=50：11.9 QPS
    • 速度几乎不随候选库规模增长而变慢

    2.4 关键工程问题¶

    生成式检索的速度与候选库规模无关：传统嵌入检索需要对全量候选库做最近邻搜索，候选库越大越慢。GENIUS 将候选编码为离散 ID，检索变成 T5 的 beam search——无论候选库多大，每步只查 Trie 的子节点集合，生成完整 9 位 ID 的复杂度为 O(1)。

    为什么推理时不调用 RQ，却还要训练它：RQ 在 Stage 1 被"学习"出来，在 Stage 2 和离线索引阶段被"读"出来用，到在线推理时虽然不被直接查阅，但它的作用通过三条路径保留下来：

    1. 给 candidate 分配 ID：T5 训练需要 ground-truth 标签，这些标签就是 RQ 对每个候选查码本得到的 9 位 ID
    2. 构建 Trie：Trie 中所有合法路径都来自 RQ 产出的 ID
    3. 让 ID 有语义结构：残差量化使相似文档共享 ID 前缀，T5 才能学到 "query → ID" 的泛化规律，而不是死记硬背

    Beam Search 原理：每步保留 K 个最可能的局部序列（beams）。初始把起始 token 复制成 K 个 beam；每步对每个 beam 预测下一个 token 的概率，把所有“beam + 候选 token”组合的累计概率排序，取前 K 个作为新 beams；重复直到生成结束符或最大长度，最后返回概率最高的 K 条完整序列。K=1 即贪心解码。

    beam size 的权衡：beam=1 退化为贪心，容易局部最优；beam 越大搜索越充分、精度越高，但延迟线性上升，且 beam 间容易趋同。论文默认 beam=10 是速度与精度的平衡点。

    精度与效率的取舍：在时尚子集（Fashion200K、FashionIQ）上，生成式方法精度仍低于嵌入式基线 CLIP-SF；但在大规模通用检索场景下，GENIUS 以显著降低的存储与延迟取得了有竞争力的精度。

    2.5 存储与效率¶

    存储效率（论文 Table 7）：

    方法 表示格式 每条候选存储
    CLIP 768 维 float32 向量 768 × 32 bit = 24,576 bits ≈ 3 KB
    GENIUS 1 个 2-bit 模态码 + 8 个 12-bit 语义码 2 + 8×12 = 98 bits ≈ 12.25 bytes

    GENIUS 每条候选仅占 98 bits（约 0.012 KB），相比 CLIP 的 3 KB 节省 99% 以上 的存储。论文举例：100 万条候选用 CLIP 索引约需 3 GB，而 GENIUS 仅需 12 MB。

    训练效率（论文附录 B.2）：

    • 1.1M 样本、4×RTX 3090 条件下：
    • CLIP-SF encoder：91h
    • 残差量化器：0.4h
    • T5 生成器：2h
    • 按单样本计算，GENIUS 比 GRACE（Flamingo-3B，0.1M 样本训练 24h）高约 2.8 倍效率

    推理效率（论文 Section C.3）：

    • 单张 RTX 3090，文搜图任务：
    • beam=30：19.6 QPS（≈51 ms/query）
    • beam=50：11.9 QPS
    • 速度几乎不随候选库规模增长而变慢；作为对比，CLIP + 最近邻检索在候选库增大时速度明显下降
    • GENIUS 吞吐约为 GRACE（Flamingo-3B）的约 4 倍

    候选库规模扩展性：

    生成式检索的核心优势在于：无论候选库是 10K、100K 还是 5.6M，T5 每步只查 Trie 的当前子节点，生成完整 9 位 ID 的复杂度始终是 O(1)。这与嵌入式检索需要对整个候选库做最近邻搜索有本质区别。

    3.3 Loss 设计¶

    三层递进，每层解决一个不同粒度的问题：

    • Sample-level CE：先在样本内对 token 取均值，再对 batch 取均值，使每条样本权重相等，解决长文本任务（Caption 200+ token）淹没短分类任务（AD 1 token）的问题
    • Restricted CE：只在 AD 标签位置额外计算 loss，且仅在"正常"/"异常"两个候选 token 上做 softmax，消除 150K 词表的先验偏置，解决 AD gen F1=0 的问题
    • 异常加权：对真实标签为异常的样本，loss 乘 ~8 倍权重，解决正常样本远多于异常样本的类别不平衡问题

    三层叠加后 AD gen F1 从 0 提升到 0.767。

    3.4 关键工程问题¶

    DDP + 全冻结 LLM 死锁：冻结参数无梯度，DDP reducer 等待所有参数梯度后才同步，全冻结时永久阻塞。解决方案：改用 device_map="auto" 替代 DDP，30B 模型自动按层切到多卡。

    跨卡 logits device mismatch：device_map 将 lm_head 切到 cuda:1，labels 默认在 cuda:0，计算 loss 时 device 不一致报错。解决方案：手动将 labels gather 到 logits 所在卡。

    显存 OOM：30B 模型 + max_length=8192，激活值过大。解决方案：gradient checkpointing（省激活值显存）+ BF16 混合精度（所有张量减半）+ 梯度累积（拆 batch）三件套叠加，显存降 60%，速度降 30%。

    Qwen3 thinking 干扰结构化输出：Thinking block 中生成的中间推理文本包含错误数字，解析器提取到错误值，导致 TTE MAPE=99.6%、TMI Acc=5.4%。解决方案：system prompt 加 /no_think 关闭 thinking，TMI Acc 5.4% → 84%。
