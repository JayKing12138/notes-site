    〇、两个阶段各启动什么脚本¶

    0.1 SFT 阶段¶

    sbatch LLaMA-Factory/jobs/finetune.sh

    完整调用链：

    sbatch jobs/finetune.sh              # 提交作业，SLURM 分配 8 个节点
  └→ srun（每节点启动 1 个 task）
       └→ llamafactory-cli train examples/train_full/qwen3vl_full_sft.yaml
            ├── 读 yaml：Qwen3-VL-8B、full 微调、bf16
            ├── 读 ds_z3_config.json：DeepSpeed ZeRO-3 分片
            ├── 读 dataset_info.json：加载 radvlm_dataset（ShareGPT 格式）
            └── HF Trainer 训练循环：forward → loss → backward → step

    涉及的文件只有 4 个：

    文件 作用
    jobs/finetune.sh SLURM 启动脚本（MASTER_ADDR、NODE_RANK、torchrun）
    examples/train_full/qwen3vl_full_sft.yaml 训练配置（模型、数据、超参数）
    examples/deepspeed/ds_z3_config.json ZeRO-3 配置
    data/dataset_info.json 数据集注册（指向 all_train.json）

    ⚠️ 坑：finetune.sh:33 实际写的是 qwen2_5vl_full_sft.yaml，跑之前要手动改成 qwen3vl_full_sft.yaml。

    0.2 RL（GRPO）阶段¶

    以报告生成任务为例，只需要启动一个脚本：

    sbatch verl/jobs/report_radcliq_run.sh

    一次 sbatch，SLURM 在 9 个节点上各跑一份这个脚本的副本，脚本内部靠 SLURM_PROCID 自动分成三种角色——训练、reward server、Ray worker 都是它自己拉起来的，不需要手动启动第二个脚本。

    大脚本 report_radcliq_run.sh 的内部逻辑¶

    第一段：环境准备（9 个节点都执行）

    export SLURM_GPUS=4                        # 每节点 4 张 GH200
export NCCL_DEBUG=WARN                     # NCCL 日志级别
export VLLM_WORKER_MULTIPROC_METHOD=spawn  # vLLM 多进程方式
export SAVE_PATH=$SCRATCH/checkpoints/${SLURM_JOB_NAME}   # checkpoint 目录
uv pip install --system -q evaluate fastapi uvicorn httpx  # 运行时装依赖

    第二段：节点角色分配（9 个节点都执行，算出两个关键 IP）

    NODES_ARR=($(scontrol show hostnames "$SLURM_JOB_NODELIST"))
MASTER_NODE=${NODES_ARR[0]}     # 第 0 个节点 → Ray head + verl trainer
REWARD_NODE=${NODES_ARR[1]}     # 第 1 个节点 → reward server

export MASTER_NODE_IP=$(srun ... -w "$MASTER_NODE" hostname --ip-address)
export REWARD_NODE_IP=$(srun ... -w "$REWARD_NODE" hostname --ip-address)
export WORKER_BASE_PORT=9400              # reward worker 起始端口
export WORKER_NUM_GPUS=4                  # reward 节点 4 张卡
export WORKER_INSTANCES_PER_GPU=8         # 每卡 8 实例 → 4×8=32 个 worker
export RAY_ADDRESS="${MASTER_NODE_IP}:6553"

    第三段：按 PROCID 三分支（每个节点只走自己那条）

    if [[ $SLURM_PROCID -eq 0 ]]; then
  # ── 角色 1：Ray head（节点 0）──
  ray start --head --node-ip-address=$MASTER_NODE_IP --port=6553 \
    --num-cpus=288 --num-gpus=4 --block &

elif [[ $SLURM_PROCID -eq 1 ]]; then
  # ── 角色 2：Reward server（节点 1）──
  cd ../RadEval && uv pip install --system .     # 装 RadCliQ 评测库
  nvidia-cuda-mps-control -d                     # 启动 MPS，让 8 进程共享 1 卡
  for inst in 0..7; do
    for gpu in 0..3; do
      CUDA_VISIBLE_DEVICES=$gpu uvicorn worker_radcliq:app \
        --host "$REWARD_NODE_IP" --port $port --workers 1 &   # 端口 9400-9431
      port=$((port+1))
    done
  done
  wait                                           # 阻塞，保持 32 个 worker 运行

else
  # ── 角色 3：Ray worker（节点 2-8）──
  ray start --address=$RAY_ADDRESS --num-cpus=288 --num-gpus=4 --block &
fi

sleep 10 && ray status    # 等集群组好

    第四段：主训练命令（只有节点 0 执行）

    if [[ $SLURM_PROCID -eq 0 ]]; then
python3 -m verl.trainer.main_ppo \
    algorithm.adv_estimator=grpo \                       # 用 GRPO 算 advantage
    data.train_batch_size=512 \                          # 每 step 512 条 prompt
    actor_rollout_ref.model.path=${MODEL_PATH} \         # SFT 产出的 RadVLM
    actor_rollout_ref.actor.optim.lr=1e-6 \
    actor_rollout_ref.actor.use_kl_loss=True \
    actor_rollout_ref.actor.kl_loss_coef=0.01 \
    actor_rollout_ref.actor.kl_loss_type=low_var_kl \    # k3 估计器
    actor_rollout_ref.actor.clip_ratio_low=0.20 \        # 非对称 clip 下界
    actor_rollout_ref.actor.clip_ratio_high=0.28 \       # 非对称 clip 上界
    actor_rollout_ref.rollout.name=vllm \                # rollout 引擎用 vLLM
    actor_rollout_ref.rollout.n=8 \                      # G=8：每 prompt 生成 8 条
    actor_rollout_ref.rollout.gpu_memory_utilization=0.6 \  # vLLM 最多占 60% 显存
    custom_reward_function.path=".../custom_rewards/radcliq_reward.py" \  # reward 函数
    reward_model.reward_manager=naive_pool \             # 512 线程并行 reward manager
    trainer.nnodes=8 trainer.n_gpus_per_node=4 \         # 8 节点 × 4 卡 = 32 卡训练
    trainer.total_epochs=1

srun --overlap --ntasks=${SLURM_NNODES} ray stop --force   # 训练完关掉 Ray 集群
fi

    九个节点的作用 🚗¶

    节点 角色 跑什么 GPU 用途
    节点 0 Ray head + verl trainer ray start --head + python3 -m verl.trainer.main_ppo 4 张卡参与训练（也被 Ray 调度放 Worker）
    节点 1 Reward server MPS + 32 个 uvicorn（worker_radcliq:app，端口 9400-9431） 4 张卡跑 RadCliQ 的 3 个评测模型，每卡 8 实例
    节点 2-8（7 台） Ray worker ray start --address=节点0:6553 4×7 = 28 张卡注册进 Ray 资源池，等 Ray 派训练进程

    卡数账目：训练卡 = 节点 0 的 4 张 + 节点 2-8 的 28 张 = 32 张（对应 trainer.nnodes=8 × n_gpus_per_node=4）；打分卡 = 节点 1 的 4 张；合计 9 × 4 = 36 张 GH200。

    各节点具体职责：🚗

    • 节点 0（大脑）：Ray head 是集群调度中心，维护资源表；verl trainer 跑训练主循环（Controller），每步通过 Ray RPC 指挥各 Worker；同时自己的 4 张卡也被调度放了 Actor/Ref/Rollout 进程——指挥和干活都做。
    • 节点 1（裁判）：完全独立于 Ray 集群，不参与训练；32 个 FastAPI worker 并行给 4096 条回答打 RadCliQ 分；单独占一台是因为 3 个评测神经网络会和训练的 FSDP 权重争显存。
    • 节点 2-8（工人）：只跑 ray start daemon，本身不执行训练代码；Ray 把 Actor（FSDP 训练）、Reference（KL 前向）、Rollout（vLLM 生成）进程调度到它们的卡上——训练的前向/反向/生成大部分发生在这 28 张卡上。

    一句话：1 台指挥兼干活（节点 0），1 台专职打分（节点 1），7 台纯干活（节点 2-8）；训练 32 卡、打分 4 卡。

    一句话总结：一个脚本、一次 sbatch、9 份副本、三种角色——节点 0 当 Ray head 并跑 verl 训练，节点 1 拉起 32 个 RadCliQ reward worker，节点 2-8 加入 Ray 集群贡献 GPU；训练进程通过 Ray 被调度到 8 个训练节点的 32 张卡上，reward 请求走 HTTP 发到节点 1。

    ⚠️ 易混点：vLLM 和 reward server 是两个不相干的组件。vLLM（Rollout）负责"生成"——给每条 prompt 采样 8 条回答，跑在训练节点上；reward server 负责"打分"——因为 RadCliQ 要跑 3 个神经网络，才单独占一个节点。

    与 SFT 的本质区别：SFT 所有节点跑同一份代码（只是 rank 不同）；RL 三种角色跑完全不同的代码。

    另注：视觉定位任务是独立的一次 RL（sbatch grounding_run.sh），从同一个 SFT checkpoint 出发另训一个模型；它的 reward 是本地几何计算，没有 reward server 角色，其余逻辑相同。

    • 每卡 2GB ≠ 显存空着：2GB 只是被 ZeRO-3 分片的"模型状态"，显存大头是不被分片的部分： | 项 | 是否分片 | 说明 | |---|---|---| | 激活值 | ❌ | 每卡自己 batch 的前向中间结果，反向要用——大头。VLM 一张图 300-400 visual token，8B 模型 batch=1 也能吃几十 GB（所以 141GB 的 GH200 也只开 per_device_batch=1） | | all-gather 临时缓冲 | ❌ | ZeRO-3 算某层时要临时拼出该层完整权重，prefetch 会同时持有几层 | | 通信 bucket / CUDA context / 碎片 | ❌ | 若干 GB |

    64 张卡的目的不是显存而是吞吐（1M 样本 × 2 epochs），模型状态摊薄后省下的显存都换成了更大的激活空间和训练速度。 - stage3_gather_16bit_weights_on_model_save: true：存 checkpoint 时 all-gather 拼回完整权重。 - auto 字段由 LLaMA-Factory 传入的训练参数自动推断（train_batch_size = per_device × grad_accum × world_size）。

    3.1 GRPO 核心公式的代码实现¶

    core_algos.py:265 compute_grpo_outcome_advantage：

    scores = token_level_rewards.sum(dim=-1)     # (4096,) 每条回答总 reward

    id2std[idx]  = torch.std(scores_tensor)

    scores[i] = (scores[i] - id2mean[index[i]]) / (id2std[index[i]] + epsilon)  # ★ GRPO 核心

    要点： - GRPO 用组内相对优势 (R - mean)/std 替代 PPO 的 Critic——"砍掉价值函数"的代码落点就在这。 - index 是 uid：每条 prompt 分配 uuid 后 batch.repeat(8)，所以 G=8 不是 vLLM 的 n=8，是 trainer 层 repeat + 温度采样。 - 边界处理：组内只有 1 条时 mean=0、std=1（:312）。 - norm_adv_by_std_in_grpo=False → 不除 std → Dr.GRPO 变体。

    3.2 非对称 clip + Dual-Clip（文档易漏点）¶

    core_algos.py:885 compute_policy_loss_vanilla：

                                       # 本项目 [0.80, 1.28] ★ 非对称

    3.3 KL 约束：k3 低方差估计器¶

    core_algos.py:1440：

    if kl_penalty in ("low_var_kl", "k3"):
    kl = ref_logprob - logprob             # Δ
    kl = torch.clamp(kl, min=-20, max=20)  # 数值稳定
    ratio = torch.exp(kl)
    kld = (ratio - kl - 1).contiguous()    # k3 = exp(Δ) - Δ - 1
    return torch.clamp(kld, min=-10, max=10)

    配置 use_kl_loss=True, kl_loss_coef=0.01, kl_loss_type=low_var_kl → 总损失 L = pg_loss + 0.01 × k3（KL in loss，不在 reward 里扣）。

    要点： - k3 由 control variate 推导（E[exp(Δ)-1]=0），Δ≈0 时二阶泰勒 ≈ Δ²/2：方差远低于 k1，且恒非负。 - 双重 clamp（Δ∈±20，kld∈-10~10）防数值爆炸。 - k3+ 变体（:1404-1414）：k1/k3 期望无偏但梯度有偏，k3+ 用 straight-through——前向输出 k3 的值，反向用 k2（0.5Δ²）的梯度：

    四、Actor / Ref / Rollout 多副本分离架构¶

    4.1 为什么要分离（面试必问）🚗¶

    副本 引擎 内存特点
    Actor（训练） FSDP 权重分片、动态分配，另有梯度 + 优化器状态
    Rollout（推理） vLLM 需要完整权重 + 启动时预分配 KV cache 池（PagedAttention），静态布局
    Reference（冻结） FSDP + CPU offload 只做前向算 log π_ref

    冲突根因：vLLM 预分配 KV cache 池后，FSDP 没有连续显存做 all-gather；FSDP 的分片权重 vLLM 又读不了。两个内存管理器互不感知 → 无法共享同一份权重 → 存两份，每步同步。

    4.2 模式切换代码（Hybrid Engine）¶

    fsdp_workers.py:636：

    async def rollout_mode(self):
    """训练模式 → 推理模式"""
    aggressive_empty_cache(force_sync=True)
    if self._is_offload_param:
        load_fsdp_model_to_gpu(self.actor_module_fsdp)   # offload 的权重先搬回 GPU

    # ★ 核心：FSDP 分片(DTensor) → full_tensor() all-gather 拼完整权重
    per_tensor_param = (
        (name, param.to(device, non_blocking=True).full_tensor()
               if isinstance(param, DTensor) else param)
        for name, param in params.items()
    )
    await self.rollout.update_weights(per_tensor_param, ...)   # 灌入 vLLM
    if self.config.rollout.free_cache_engine:
        await self.rollout.resume(tags=["kv_cache"])           # 唤醒 KV cache

async def trainer_mode(self):        # :719

    if self.config.rollout.free_cache_engine:
        await self.rollout.release()  # vLLM sleep，还显存给 FSDP

    要点： - full_tensor() 触发 NCCL all-gather——每步权重同步的开销来源，是 verl 跑 GRPO 的主要工程成本。 - 本项目 free_cache_engine=False：GH200 141GB 够大，vLLM 常驻不 sleep，省掉 wake_up 延迟。 - vLLM 用 load_format="dummy" 启动：不加载真实权重（随机占位），真权重由 update_weights 灌入——可以提前初始化 KV cache 池。 - 生成入口 generate_sequences（:893）：rollout_mode() → vLLM generate → trainer_mode()，对 trainer 透明。

    def soft_f1_hungarian(predicted_boxes, actual_boxes, min_iou=0.0):
    ious = _iou_matrix(predicted_boxes, actual_boxes)     # 两两 IoU
    row_ind, col_ind = linear_sum_assignment(1.0 - ious)  # ★ Hungarian 一对一匹配
    matched_ious = ious[row_ind, col_ind]
    tp_mass = matched_ious[matched_ious > min_iou].sum()  # soft TP：按 IoU 加权
    fp_count = n_pred - num_valid_matches
    recall    = tp_mass / n_gt
    precision = tp_mass / (tp_mass + fp_count)
    return 2 * P * R / (P + R)

    要点：

    • 为什么 soft-F1 而不是 mAP：mAP 是阶跃函数（IoU > 阈值才算对），reward 信号不连续；soft-F1 让 IoU=0.6 的框贡献 0.6 的 credit，对 RL 更友好。
    • 纯 scipy 几何运算，无神经网络 → 内联在 verl worker 里跑，不需要 server。
    • bbox 用正则从生成文本提取（:7-29），支持负数/科学计数法，非有限值丢弃。
    • 已知瑕疵：compute_iou 定义了两遍（:33 和 :47），第二个覆盖第一个。

    6.3 客户端：轮询 + 指数退避重试¶

    verl/custom_rewards/radcliq_reward.py：

    endpoints = [f"http://{REWARD_NODE_IP}:{9400+i}" for i in range(32)]

def _next_endpoint():                    # 线程安全轮询（round-robin 负载均衡）
    with _counter_lock:
        i = _counter.value; _counter.value = i + 1
    return endpoints[i % 32]

def radcliq_score(pred, true, retries=3, timeout=5):
    backoff = 0.1
    for attempt in range(retries + 1):
        r = requests.post(f"{_next_endpoint()}/score_radcliq", json={...}, timeout=timeout)
        if r.status_code == 200:
            return r.json()["score"]
        if r.status_code in (429, 500, 502, 503, 504):      # 只重试可恢复错误
            time.sleep(backoff + random.random() * backoff)  # ★ 指数退避 + 抖动
            backoff *= 2

    八、面试高频追问速答¶

    Q: GRPO 和 PPO 的区别，代码上体现在哪？ A: 砍掉 Critic。代码上没有 CriticWorker，advantage 直接在 compute_grpo_outcome_advantage 里按 uid 分组算 (R-mean)/std，不需要价值函数前向。

    Q: 为什么 Actor 和 Rollout 权重相同却要存两份？ A: FSDP 分片 + 动态分配 vs vLLM 完整权重 + 预分配 KV cache 池，内存布局不兼容。每步用 full_tensor() all-gather 后 update_weights 灌入 vLLM，这个同步是主要工程开销。

    Q: reward server 为什么用 32 个副本 + 512 线程？ A: RadGraph 不支持 batch inference，单实例慢；每 step 4096 条回答要打分。32 个 FastAPI worker（4 GPU × 8 实例，MPS 共享）横向扩吞吐，客户端 round-robin + 指数退避，trainer 侧 512 线程掩盖 HTTP 延迟。

    Q: 训练稳定性怎么保证？ A: 三道保险：非对称 clip [0.80,1.28] 管单步（另有 Dual-Clip c=3.0 防负优势爆炸）；KL in loss（0.01×k3）管全局偏移；k3 估计器本身低方差恒非负（必要时 k3+ 用 k2 梯度做 straight-through）。

    Q: reward hacking 遇到过吗？ A: 单用 RadGraph-F1 时报告长度 207→93 字符——模型学会写极短报告避免错误实体。解法是 RadCliQ 复合指标（实际是 RadGraph/BERTScore/CheXbert 三者加权，BLEU 权重≈0）。
